The top row is what the radio says it is on — rigctl f, asked of the IC-9700 itself. The second is the correction Skyfield computed. Showing both is the point: a display that only echoes what the software commanded cannot tell you the radio ignored it, which is exactly the failure that wasted an evening on SatPC32's CAT. Nothing here is clickable — Gpredict drives, this observes.

The piece that pays for itself

Keps health

Build this first. It needs no hardware, no pass, and no interface decisions — and it's the gap that actually bit.

nasabare.txt 99 TLEs Newest epoch 2 h ago · AMSAT
GROUP=amateur 96 TLEs Newest epoch 6 h ago · Celestrak
GROUP=last-30-days 0 TLEs Valid group, empty today — not a fault
celestrak.com (old) 404 Dead since the .org move — this is what rotted

Each card counts TLE lines, never HTTP status. Celestrak answers a bad group with 200 OK and an Invalid query body — a status check calls that success, which is precisely how the problem hid for seven months.

Decisions before code
01

Which concept is the product? A and C could ship together — the same reader feeding two views. B needs pass prediction, which means either scraping SatPC32's own list or adding SGP4, and that is the one place this could quietly become a tracker.

02

The architecture changed on 29 Aug. SatPC32's DDE feed is gone as a dependency — Skyfield computes the pass locally and rigctl on 4532 reads the radio back. Proven that night: engaging Gpredict moved the IC-9700 to 145.800 MHz, confirmed by asking the radio, with no CI-V address, COM port or baud rate involved.

03

Full duplex is unresolved. AetherSDR deliberately reports satellite mode off to Hamlib. If a V/U bird can't run both directions at once, the uplink row in Concept A is showing something the radio isn't doing.
